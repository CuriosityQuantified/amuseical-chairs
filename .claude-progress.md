## Current state (2026-07-30, later)
- Same branch, second pass: making the graph **actually get used and actually stay current**, because the first pass only documented it. Two mechanisms, one per half.
- **Used:** `.mcp.json` registers graphify as a project MCP server, so an assistant in this repo gets 10 native tools (`query_graph`, `get_node`, `get_neighbors`, `get_community`, `god_nodes`, `graph_stats`, `shortest_path`, plus 3 PR tools) instead of a bash command it has to remember. Verified over stdio by hand: `initialize` → `serverInfo {name: graphify, version: 1.29.0}`, `tools/list` → 10, and `tools/call god_nodes` / `shortest_path` return real answers off the committed graph. ⚠️ **Needs the `mcp` extra** — `uv tool install "graphifyy[mcp]"`. Plain `graphifyy` installs the `graphify-mcp` executable but not the `mcp` package, so the server dies on `ModuleNotFoundError` at startup. `.mcp.json` calls `graphify-mcp` as a bare PATH-resolved command on purpose: unlike a hook, a missing MCP server just fails to start and says so, it does not break every Read.
- User chose the soft nudge over `--strict` (which would block the first raw source read per session). Nothing in this repo denies a plain grep.
- **Current:** `scripts/check.mjs` **rule 7** fails when the graph is stale, and CI already runs `npm run check`. Freshness is by **content hash**: `graphify-out/graph-lock.json` (path → md5, sorted) is distilled from graphify's manifest by `scripts/graph-lock.mjs`, and `npm run graph` / `graph:rebuild` regenerate it. Rule 7 catches an edited file, a deleted file, and a new never-indexed module.
- ⚠️ **Two freshness designs that DO NOT work — do not "simplify" rule 7 back into either.**
  - Comparing `built_at_commit` to HEAD: the graph records the commit it was built from and can never record the commit that adds it, so a single commit carrying both always reads one behind.
  - Requiring `graph.json` in the same diff as the code (co-change): **this was written first and the mutation test caught it.** It diffs merge-base..HEAD, so the commit that first added the graph satisfies it for the entire life of the branch — I changed `shared/rng.js`, committed without touching the graph, and check stayed green. Content hashing has no such hole and needs no git history, so it also holds in a shallow clone.
  - Rebuilding in CI and diffing would be flaky anyway: Leiden re-clusters identical code differently (watched it go 17 → 20 → 19 → 21 → 23 communities across rebuilds).
- Rule 7 mutation-tested four ways: edited `shared/rng.js` → fires; deleted `public/js/chairs.js` → fires; added `shared/brandnew.js` → fires ("new, never indexed"); deleted lock → fires. ⚠️ Deleting a file that `check.mjs` transitively imports (e.g. `shared/ciede2000.js`) crashes check.mjs at import time instead of reporting cleanly — **pre-existing**, reproduced with rule 7 stubbed out, still exits non-zero.
- **Merges:** `.gitattributes` assigns `graphify-out/graph.json` the union merge driver (`merge=graphify`) — committed. `graph.json` is ~13k lines of generated JSON that two branches will both touch, and the realistic outcome of a conflict in a generated file is somebody deleting the graph. The driver half lives in git config (per-machine, `npm run graph:setup`); git silently falls back to a normal text merge without it, so the committed `.gitattributes` is safe either way.
- `npm run graph:setup` = `graphify install --project && graphify hook install` — one command for the whole per-machine side: skill, PreToolUse nudge, post-commit rebuild, merge driver. `manifest.json` stays gitignored (per-file mtimes = checkout time on a fresh clone, so committing it would churn all 40 entries on every machine's first rebuild).
- ⚠️ Rejected `fetch-depth: 0` in ci.yml — added it for the co-change rule, then removed it when rule 7 became hash-based. Hash comparison needs no history; don't re-add it for this.
- **Two hashes, two severities** — the subtlety worth not undoing. graphify's manifest keeps `ast_hash` AND `semantic_hash`, and blanks the semantic one when a file changes. `npm run graph` (AST-only) refreshes `ast_hash` but never re-reads a doc, so a lock keyed on `ast_hash` alone reports a rewritten README as fresh while its doc nodes still describe the old prose — a false green. So the lock records both: rule 7 **hard-fails** on `ast` (free to fix, `npm run graph`) and **warns** on `semantic` for `.md`/`.html`/`.yml` (fixable only by `npm run graph:rebuild` with a backend, which CI does not have and should not gate on). Verified both ways: the warning listed README/progress-log/ci.yml after a doc edit, and cleared after a full `graphify extract . --backend claude-cli`.
- Graph after this pass: a few hundred nodes across a couple dozen communities. **Exact counts live in `GRAPH_REPORT.md`, deliberately not in prose** — every edit to the docs that describe the graph changes the graph, so a hardcoded number here is wrong by the next commit. Note `npm run graph` reports community drift and renames some by their hub — `graphify label .` refreshes names.

Host ✕ works on the single projected fact (`hideEntry` handles `clientData.factId` as well as pooled `entries`), voiding it for everyone and hiding its author.
- ⚠️ Two landmines fixed while building this: `setPhase` spread `{name, ...data}` so a payload field called `name` **shadowed the phase name** — now `{...data, name}`, and the reveal uses `authorName`. And `Room.stageHistory()` must slice to `gameIndex + 1`: a variable-length game queues every stage up front, and the unplayed ones must not be revealed or scored.
